# Agency departure completion

Agency Owner/Manager with `tour:update-own` closes a **departure**, not a catalog tour or each passenger. Active membership and permissions are checked again inside the transaction. Tenant ownership is checked for every read/write.

## HTTP

- `GET /agency/completions?page=1&status=pending`: ended departures with CONFIRMED bookings, 20 per page, `hasNext` (default status).
- `GET /agency/completions?page=1&status=completed`: Agency-scoped completed departure history, newest completion first. Includes `completedAt` and `hasReport`; historical completed bookings without an Agency report remain visible and are explicitly labeled as legacy completions. No reports are invented. Owner/Manager access matches the pending queue.
- `GET /agency/tours/:tourId/departures/:departureId/completion`: frozen snapshot, eligible bookings and immutable report history. Opens after departure.
- `POST .../completion/draft`: appends a draft; changes no booking status.
- `POST .../completion/submit`: appends a submitted report, completes that departure's CONFIRMED bookings, records audit and enqueues durable delivery in one transaction. Later submissions are amendments requiring a reason; they do not re-complete or resend.

The Agency report opens in a modal over `/agency/completions`, without leaving the pending/history list. Notification/calendar links use `?tourId=...&departureId=...` to open the same modal; older report and tour-detail completion routes redirect there. Its eight sections cover age-group attendance, summary, changes, service confirmation, absence handling, incidents, uploaded images and additional notes. The modal retains persistent save/submit actions and has no departure picker, actual-end input or per-booking attendance list.

New optional JSON fields: `noChanges`, `noIncidents`, `serviceConfirmations: [{key, status}]`, `absenceReason`, `additionalNotes`. Service confirmation refers to add-ons actually purchased in eligible bookings, not generic transport/guide/ticket inclusions. `bookedServices` is computed from each booking's `serviceSnapshot`, grouped by service identity and checkout terms, with name, unit, quantity and booking count; canceled and pending bookings are excluded. No passenger identities or pickup addresses are exposed. Submission requires exactly one non-UNCONFIRMED confirmation per purchased group (`PROVIDED`, `NOT_PROVIDED`, `PARTIALLY_PROVIDED`). Unknown and duplicate keys are rejected; drafts can remain unconfirmed. The server freezes the authoritative service list into each report revision. Catalog edits cannot rename a previously purchased service. Trips without add-ons show an explicit empty state and require no service confirmations. The old fixed `services` object remains readable as a legacy template and is not used for new forms.

Changes/incidents require 10+ characters when their corresponding no-change/no-incident flag is false. Absence handling is separate from incidents: with the new field present, headcount differences require `absenceReason` of 10+ characters; older clients retain their incident-explanation fallback. Submitted flags and text must agree. Drafts allow incomplete content. All fields are retained per immutable revision and exposed to internal read-only readers. No schema migration is required.

Images upload from the device through the existing authorized Agency `POST /agency/tours/upload-image` multipart endpoint and signed server-to-Cloudinary integration. Supported formats are JPG/PNG/WebP, 5 MB each, at most 20 per report. Returned HTTPS URLs are stored in `evidence`, restored in drafts/amendments and retained in history. Upload progress blocks saves; successful images remain when a later upload fails. Removing an image only removes it from the current version, preserving old audit evidence. This UI supports image attachments, not arbitrary document file types or typed URL inputs.

Body: `expectedRevision`, `summary` (20+ characters on submit), `changes`, `incidents`, `actualParticipants`, `actualGuests: {adults, children, infants}`, `attendance: []`, `evidence: []`, `amendmentReason`. Actual counts must be nonnegative integers within each booked age group, and their sum must equal actualParticipants. Booked groups come from checkout pricing snapshots, then complete passenger snapshots; legacy checkout without age selection uses its adult-only default. Both booked and actual groups are retained in report history and internal reads. Amendments may correct counts with a mandatory reason, append a new version and record the before/after attendance in audit. Older total-only submitted reports stay readable without inventing an actual age breakdown; their amendment can supply a new age breakdown explicitly. Actual end is optional; the server completion timestamp is retained for audit without inventing an actual trip end. Legacy per-booking attendance and evidence remain supported for older clients/history.

Headcount sums Booking.participants across eligible bookings, including adults, children and infants; it is not the number of bookings or accounts. Aggregate totals and booked headcount are frozen in each report revision. Partial attendance never gets allocated to accounts: booking attendance stays unknown (null) unless the total proves everyone attended or nobody attended. Internal report readers use the stored aggregate. Attendance differences require an absence explanation (legacy clients use incidents). Corrections update live attendance only for bookings originally completed by this report workflow; booking status/completion time, tickets, earnings and delivery records are unchanged, so completion notifications and charges are not replayed. CANCELLED/PENDING bookings are excluded. Historical COMPLETED bookings outside this workflow remain unchanged. Submitted reports retain internal booking references with nullable individual counts so the existing database guard works without a migration.

The snapshot freezes title, departure timestamp, itinerary, duration and assignment. Scheduled end comes from the latest paid booking end snapshot, falling back to departure + duration. Actual end is stored in each report revision. Existing booked end times are never silently rewritten. Catalog edits do not rewrite the snapshot.

The **Hoàn tất chuyến đi** page has **Chờ hoàn tất** and **Lịch sử hoàn tất** tabs. History links directly to the selected departure's existing report and version history; legacy rows link to departure details and explain that no Agency report exists. Tabs reset pagination; single-page and empty lists hide pagination.

Both queue responses include `coverImage` (first tour image, nullable), `destination` and `durationDays` from the owned tour. The Agency list uses compact discovery-style horizontal tour cards with a cover, destination, date range, duration, headcounts, report status and report action. Covers have a missing/failed-image fallback; cards stack on mobile. Prices, ratings, wishlist and sales descriptions are omitted.

The internal submitted-report list uses the same `CompletionTourCard` component. Its read model includes the tour cover/destination, frozen duration and scheduled end, and aggregate COMPLETED booking/guest counts scoped to the same agency, tour and departure. Moderator cards keep the latest author and amendment indicator; their action is a link to the existing read-only report page. Agency actions continue opening their report modal. No passenger/contact details are added to the list response.

## Internal read-only access

Moderator and Super Admin receive `tour-completion:view`. Only these two roles can access `GET /moderation/tour-completions` and `GET /moderation/tour-completions/:id`; delegating this permission to a traveler or agency does not open internal reports. There are no mutation endpoints. Lists support page, tour title (`q`), agency name (`agency`), agency ID and completion-time range (`from`/`to`).

`GET /moderation/tour-completions/by-booking/:id` resolves the report from a complaint's booking. Responses include only submitted versions, aggregate attendance, evidence links and author names. Draft-only reports return 404; drafts, passenger papers/contact details and booking attendance identifiers are not returned. Viewing never creates a report, changes a booking or emits audit/notification events.

The Moderator menu places **Tổng kết tour** under **Chất lượng & Nội dung**, separately from violation reports. The landing page is an Agency directory: `GET /moderation/tour-completions/agencies?page=1&q=...` returns every AgencyProfile, including unverified agencies and agencies without submitted reports, paginated at 20 with report counts and the latest completion time. Counts represent completed departures with submitted reports, not individual amendment versions. Identity cards include the available avatar, business address and actual verification status; missing/failed avatars use name initials. No contacts or verification documents are exposed. Clicking a card navigates to `/moderator/tour-completions/agencies/:agencyId`; `GET /moderation/tour-completions/agencies/:id` provides its metadata directly, including zero-report agencies. The agency page lists submitted reports via the existing `agencyId` filter; title/date filters and report pagination stay scoped to that agency. Report detail links back to its agency. This area is read-only and has no approval workflow.

## Jobs and reliability

- Every five minutes: remind at scheduled end +24h, at most once per day, label overdue after +72h. Only Owner/Manager tour management recipients should act on it. Reminders never complete bookings.
- Every minute: process at most 100 durable delivery items. Each booking's ticket, guide earning, traveler notification, guide notification, retryable email and delivery acknowledgement commit together. A row lock and unique booking key prevent duplicate delivery across workers. Failure rolls back and schedules exponential retry capped at one hour. Guide/fee are frozen at close-out.
- Reviews remain optional and one per owned COMPLETED booking. Entirely absent groups cannot review; they receive a completion/absence notice with a contact instruction instead.
- Older traveler/guide completion endpoints return `409 AGENCY_COMPLETION_REQUIRED`; the old automatic completion method is a no-op.

## Deployment

Migration: `20261116000100_agency_tour_completion`. Apply using the normal Prisma deployment process **before** starting the new worker. During cutover stop old-version maintenance workers (`JOBS_ENABLED=false` or stop them) so the retired automatic job cannot close bookings while deploying. Run one or more new workers with `JOBS_ENABLED=true`. Jobs scan persisted due timestamps, so downtime does not discard reminders/deliveries.

Migration `20261117000100_require_agency_report_for_completion` adds a database guard against old application workers sharing the same database: an UPDATE into COMPLETED requires a submitted report for the same Agency/tour/departure with attendance for that booking. The report service writes that report before updating bookings in the same transaction. Drafts do not authorize completion. The guard does not rewrite existing history or prevent importing historical COMPLETED rows. Old workers will log rejected completion attempts until upgraded or disabled. This migration passed disposable local PostgreSQL tests and was applied to the configured Production database on 2026-11-17 after explicit user approval, with its exact SHA-256 migration-history entry in the same transaction; no existing booking rows were changed.

No historical reports or audits are fabricated. No data reset or seed is required. The migration was tested on disposable local PostgreSQL and subsequently applied to the configured Production database to restore booking queries. Prisma CLI failed with a schema-engine error; the exact migration file and its SHA-256 migration-history entry were committed together in one database transaction. Avoid rolling back to an old automatic-completion worker without disabling that job.
