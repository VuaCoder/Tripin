# Agency operations UI

- `/agency`: backend dashboard; revenue totals and a separate empty state for the rolling 30-day series.

The overview uses a Tripri-green bento grid: three lifetime financial metrics, a larger revenue chart beside the top-tour ranking, then booking/tour status panels. Chart range is 30 days (backend rolling window) or the last 7 UTC calendar days, grouped into Monday-based weekly bars without changing totals. No month-over-month percentages or six-month figures are inferred. The daily table remains available for exact values; missing tour photographs use ranking markers rather than unrelated stock imagery.
- `/agency/bookings`, `/agency/tours`: permission-scoped operations.
- `/agency/settings`: partner profile and the existing local commission calculator. This calculator does not update contractual commission rates.
- `/agency/notifications`: the authenticated user's inbox, pagination and read actions.

`components/AgencyRightSidebar.tsx` retains its old export for Header compatibility, but renders the **left** navigation rail. It starts open on desktop and has exactly two click-controlled modes; pointer hover/focus never changes the state, preventing the rail from jumping open under the cursor. The header toggle and search shortcut remain accessible alternatives; touch uses the toggle/backdrop. The Tripri brand mark remains visible when collapsed. The notification bell sits beside the avatar/company name in the footer; clicking the avatar opens Cài đặt and Đăng xuất actions. The name comes from `agencyProfile.companyName`; commission remains a navigation entry.

Ctrl+K / Cmd+K opens and focuses the function search. It searches permitted navigation labels/groups, ignoring Vietnamese accents; Enter opens the first match. It does not query customer, booking or tour records. Functions navigate to routes; no business forms render inside the sidebar. Collapsed navigation uses equal grid tracks, with group titles hidden instead of reserving blank space. Height-responsive spacing keeps the current functions inside the rail without an internal scrolling region.

Agency layout and Agency AppShell share the sidebar CSS `shell`/`body` classes. The shell reserves the same width as the sidebar using shared CSS variables and `:has([data-expanded=true])`; the toggle, keyboard search and Escape therefore update content spacing from the actual sidebar state. The navigation list is the only scrollable region, so the footer/avatar stays pinned to the bottom as features are added. Opening pushes/reflows desktop content rather than covering it. Narrow screens keep the content's readable collapsed width and shift it sideways without creating page-wide horizontal scrolling. Transitions share timing and respect reduced motion. Toggle icons use `PanelLeftOpen` / `PanelLeftClose`; collapsed labels use `display:none`.

`notifications.ts` uses the existing `/notifications` endpoints through the shared authenticated RTK base query and connects to the backend Socket.IO gateway with `auth.token` (never in the URL). `notification:new` and reconnect invalidate the inbox/count cache. Visible pages also refresh every 30 seconds and on focus/reconnect to recover missed events/read changes from another session. The shell removes listeners and disconnects when the user/token changes or on unmount. Notification content is not copied to localStorage.

Verification: component/hook tests mock Socket.IO to cover token handshake, push/reconnect, refresh isolation and teardown. A real two-session backend smoke test is still needed to validate the deployment's socket origin/CORS/proxy configuration.

The bell opens an accessible portal dialog backed by the same `AgencyNotificationInbox` as `/agency/notifications`, not a static empty placeholder. Read/delete actions invalidate the shared inbox and unread count. Deletion requires confirmation and backend ownership checks. Search displays the Command icon + K on every OS and accepts both Ctrl+K and Cmd+K, with an explicit circular clear control.

## Agency dashboard fetching — Phase 2A

The Dashboard previously set `refetchOnMountOrArgChange: true`, so returning to `/agency` sent another HTTP request even if RTK Query held a fresh result and the backend still served its 30-second cached snapshot. `app/agency/page.tsx` now reads the cached snapshot's server `generatedAt` and uses `features/agency/dashboardCache.ts` to request again when that snapshot is missing, invalid, future-dated or at least 30 seconds old, or when its previous refresh failed. A first visit still fetches normally. Focus/reconnect refetch and the manual refresh button remain enabled for freshness while the page stays mounted. The existing identity-isolation middleware clears RTK Query data when the signed-in user ID changes; dashboard data is never keyed or reused across Agency accounts. The backend cache remains keyed by Agency ID and retains its existing 30-second policy.

The page distinguishes the first load (`isLoading` with no data) from a background refresh (`isFetching` with cached data). If a background refresh fails, it displays a warning alongside the last successful snapshot and its generation time; an initial failure still shows the full error state. No dashboard totals are computed differently. `backend/src/modules/dashboards/dashboards.controller.ts` now includes `Server-Timing: agency-dashboard-service;dur=...` on successful Agency Dashboard responses, measuring only the service call after authorization. Compare that header with the browser's total Network duration before proposing database changes; the prior 875 ms observation cannot be attributed to SQL from source alone.

Changed files: `app/agency/page.tsx`, `features/agency/dashboardCache.ts`, their focused tests, `backend/src/modules/dashboards/dashboards.controller.ts`, its route test, and this README. Frontend TypeScript and the production Next.js build passed; the two Phase 2A frontend suites passed 13 tests, the preserved Phase 1 suites passed 24 tests, and the backend dashboard route suite passed 4 tests. Bookings/Tours fetches and notification polling are reserved for later phases.

Tour editing and the per-tour workspace share a horizontal four-step navigator. Forms remain mounted in the workspace while switching steps to preserve unsaved itinerary/availability. The preview is beside the form on desktop and stacks/toggles on smaller screens; it is explicitly a preview and does not imply unsaved changes were persisted.

## Bookings and Tours fetching — Phase 2B

Opening Bookings previously requested `GET /agency/tours?page=1&limit=100` immediately, in addition to the paginated Bookings request, solely to populate the optional tour filter. The tour list now stays skipped until the user opens that filter. It then requests `page=1&limit=12`, matching the unfiltered Tour Management query's RTK Query cache key, so an in-flight request is deduplicated and a recent page is reused when switching screens. RTK Query's existing cache lifetime and tour-mutation invalidation remain unchanged; identity isolation clears the shared cache on account switch. Bookings still requests its own filtered, paginated endpoint and its authorization checks are unchanged.

The filter retains page controls and adds debounced server-side title search. `GET /agency/tours` accepts an optional `q` (maximum 100 characters); its query keeps the authenticated `agencyId` and existing archived/status rules while filtering titles before pagination. Thus a matching tour beyond the first 100 can be selected without downloading all tours. This is an additive, backward-compatible query parameter; the response shape and booking business rules are unchanged. Users without tour-management permission still use the existing manual tour-ID input and never request the tour list.

Request expectation for a fresh Bookings visit: before, one Bookings list request plus one 100-tour list request; after, one Bookings list request and zero tour-list requests until the filter opens. On first opening, one 12-tour page request; returning to Tour Management's unfiltered first page within RTK Query's default 60-second unused-cache window needs no second request. Searching or moving to an uncached page needs a separate request. A real RTK Query store test verifies in-flight deduplication, cache reuse, distinct search keys and account-switch clearing. Focused frontend tests verify lazy loading, >100-tour pagination and search arguments; backend unit tests verify search validation and Agency-scoped service forwarding. These are request-count tests, not browser network timings or a database benchmark; UAT on an authenticated Agency session should confirm transfer size and latency. Backend integration tests remain blocked by the pre-existing empty migration directory documented in Phase 2A.
